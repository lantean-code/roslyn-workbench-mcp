## Publication and execution model

`BundledCorePlugin.Configure` registers three plugin-scoped singleton services and exactly 39 singleton handlers. Catalogue preparation uses the bundled-only allowance for internal request/response types, validates their handler shapes and input schemas, and publishes two destructive tools (`rename-symbol` and `format-document`) plus 37 non-destructive queries. The Host creates closed typed MCP adapters at startup. Calls bind and data-annotation-validate the request, select a Workspace, acquire the appropriate Workspace lease, construct a snapshot-scoped plugin context, invoke the handler, detect direct live-Workspace mutation, serialize the structured result and dispose the lease.

All common handlers check cancellation before dispatch. Coordinate-bearing queries validate `ExpectedSnapshot` before resolving a `LocationSelector` or a location-backed `SymbolSelector`; name, documentation-ID and scope-only requests do not require a snapshot because they do not reinterpret caller coordinates. Both mutation contracts inherit a required snapshot. A successful mutation handler returns an immutable candidate `Solution`; the Host alone invokes the Workspace stager, which applies Unit 2's candidate validation, revision capacity and transaction rules. No bundled handler writes source files directly.

Bundled handlers do not use the public plugin `IQueryResultCache`. They benefit only from the Workspace services that cache hierarchy, target-framework or reference work under complete Workspace snapshot identities; direct `SymbolFinder`, compilation/analyzer, syntax/semantic and flow calls are recomputed. This is a deliberate execution characteristic rather than a correctness defect, but it makes pre-projection work and cancellation material for repository-scale queries.

## Representative cross-project traces

### Workspace and project projections

The Host query adapter acquires a current snapshot lease and supplies `GetSolutionStructureTool` with the immutable solution plus Workspace hierarchy and target-framework services. Hierarchy or evaluation failure becomes a retryable `ProjectStructureUnavailable`; a path that cannot be normalized becomes reload guidance. `get-project-details` uses the same target-framework and path boundaries, but independently bounds each large collection. `get-document-options` consumes Roslyn parse/compilation options and analyzer-config providers. Candidate `RWMCP2-007` arises only in the project-details compilation projection: the public payload claims effective preprocessor symbols while `CreateCompilationOptionsInfo` assigns `[]` in both branches instead of reading the project's parse options. Official Roslyn documentation places defined symbols on [`ParseOptions.PreprocessorSymbolNames`](https://learn.microsoft.com/dotnet/api/microsoft.codeanalysis.parseoptions.preprocessorsymbolnames?view=roslyn-dotnet-5.3.0), which the document-options projection already uses correctly.

### Symbol identity, search and relationship queries

Location-backed symbol resolution validates snapshot identity before Workspace resolves a UTF-16 span or copied selection. Canonical symbol references prefer documentation-comment IDs and retain project/location qualifiers; metadata symbols fall back to metadata display. Relationship tools pass project/document scopes into Roslyn or the Workspace reference service, filter to current selected documents where needed, de-duplicate with `SymbolEqualityComparer.Default` and impose deterministic display/path/span ordering before returning prefixes.

Search and relationship limits principally constrain serialization and post-discovery enrichment, not Roslyn discovery. `search-symbols`, implementations, overrides, derived types, callers, dependents, change impact, diagnostics and several analysis tools first obtain a complete result set so they can sort or publish an exact count. Current zero/one/low/high tests prove stable returned prefixes, but they do not establish proportional work. This is recorded as a repository-scale characteristic rather than a separate defect because the current Roslyn APIs used by several families do not accept a result limit and deterministic global ordering requires broader discovery. The sharper capacity violations are the unbounded nested payloads in `RWMCP2-010`.

### Dependency and impact analysis

`DependencyAnalysisService` caches semantic models only within one invocation. Graph queries discover source declarations, choose stable node prefixes, then build only edges whose endpoints remain in that prefix and stop at the edge limit. Test-impact analysis similarly stops after finding one additional matching test. Cycle analysis differs: it passes null graph limits, creates the complete graph and adjacency maps, recursively visits the whole graph, computes every strongly connected component and only then applies `CyclesLimit`. Candidate `RWMCP2-009` records both the missing cancellation boundary and unbounded call-stack depth. The existing real service test intentionally uses `CyclesLimit = 0` yet still computes a two-node cycle and total count, preserving rather than disproving the full traversal. Current [.NET documentation](https://learn.microsoft.com/dotnet/api/system.stackoverflowexception?view=net-10.0) confirms that user code cannot catch stack exhaustion and the process terminates by default, so the unbounded recursive path retains P1/High even though no fixed repository-independent overflow threshold is claimed.

### Compiler, analyzer and flow queries

Compiler-diagnostic helpers obtain project compilations, run loaded project analyzers when requested, filter results back to selected documents and preserve cancellation into Roslyn. The bundled async provider loads the copied `AsyncFixer.dll` from the application base directory in the default load context, instantiates attributed analyzers and requires exactly AsyncFixer01–06; missing, malformed or incomplete analyzer content fails provider construction at catalogue startup rather than silently omitting analysis. Analyzer service failures are surfaced after all selected project groups complete, while cancellation continues to propagate.

Control/data-flow requests accept any valid location span and advertise the selected region. Their resolver nevertheless calls `FindNode` and `FirstAncestorOrSelf<StatementSyntax>`, passes only that one statement to Roslyn and returns the original span. For an expression span, the analysis covers its complete statement but labels the expression as the region; for a span covering two adjacent statements, the smallest containing node can be the enclosing block, so analysis includes sibling statements outside the selection while the result still echoes the smaller range. Roslyn provides first/last-statement overloads specifically for a contiguous region in [`AnalyzeDataFlow`](https://learn.microsoft.com/dotnet/api/microsoft.codeanalysis.csharp.csharpextensions.analyzedataflow?view=roslyn-dotnet-5.3.0) and [`AnalyzeControlFlow`](https://learn.microsoft.com/dotnet/api/microsoft.codeanalysis.csharp.csharpextensions.analyzecontrolflow?view=roslyn-dotnet-5.3.0). Existing tests select one exact `IfStatementSyntax` or `LocalDeclarationStatementSyntax`, so they cannot detect the widening. This is candidate `RWMCP2-008`.

### Mutation staging and external filesystem boundary

`rename-symbol` and `format-document` run while the Host retains Unit 1's exclusive mutation lease. Each rejects stale snapshot input before interpreting a target, returns `NoChange` without consuming revision capacity when appropriate, and otherwise supplies only a candidate solution and summary. `PluginMutationMcpServerTool` performs the direct-Workspace containment check and calls `PluginMutationExecutionLease.StageAsync`; Workspace validates the candidate delta and appends a transaction revision. The bundled component integration test performs rename then format through the real coordinator and observes revisions 1 and 2 plus previews. Current acceptance and scenario source follows rename through commit/recovery boundaries reviewed in Unit 2. Neither handler writes files, owns a commit resource or bypasses revision capacity.

## Validation, schema and continuation behaviour

Input schemas are generated from the actual internal request types. Required selectors/new names, inherited mutation snapshots, defaults, non-negative limits and closed granularity/accessibility values are asserted by Host integration tests. Cross-field exact-one constraints are enforced by the request binder's object validation before handler execution. `BundledCorePluginTests` materializes the plugin and proves all 39 unique names/descriptions and the two destructive annotations. Optional full output schemas use the same typed object responses used at runtime; unlike candidate `RWMCP2-006`'s external scalar scenario, every bundled query response is an object record and is accepted by the successful-result serializer.

Handled selector, stale, scope and dependency failures return typed `Rejected`/`Conflict` results with centrally mapped continuation guidance such as resolve again, reload, retry or revise request. Empty semantic results are successful empty payloads. `OperationCanceledException` is not converted to a domain failure: the common handler and Roslyn/service calls propagate it through the Host's top-level filter. Unexpected analyzer/Roslyn/projection exceptions are captured by the Host's correlated unexpected-error boundary. Current tests exercise cancellation forwarding at common/plugin/Workspace boundaries but do not cancel every individual tool during its largest synchronous projection loop.

## Capacity and resource ownership

Most large top-level result collections use `BoundedCollection<T>` with deterministic order and `hasMore`/optional total count. Candidate `RWMCP2-010` identifies outer bounds that do not cap large nested branches: selected solution projects contain every document/reference; an outline recursively contains every node; a selected caller contains every call site and context; a selected duplicate group contains every occurrence and its complete normalized context; and a selected CFG block contains every operation's complete syntax text. These branches can exceed transport/memory budgets even when outer limits are zero/one/low, and several are included by a single boolean or by default.

Handlers do not acquire disposable Roslyn resources beyond the Workspace lease. Compilation, syntax, semantic and immutable solution objects remain Workspace/Roslyn owned. The only plugin-scoped external resource is the AsyncFixer analyzer set loaded into the process default context; its service has no independent unload contract. No per-call stream, file handle, load context or analyzer driver leak was found in the bundled implementations.

Those tests provide strong branch-level evidence for resolver rejection, success, empty results, filters, deterministic order and the declared outer bounds. Plugin service tests exercise real reference, hierarchy, graph, cycle and test-impact algorithms. The eight bundled component tests cross real MSBuild Workspace, plugin catalogue and transaction boundaries for representative projections, relationship queries, diagnostics/analyzers, operation/flow queries and both mutations. Host suites cover catalogue preparation, schema/binder behaviour, typed adapters, structured serialization and unexpected errors.

Current published-process acceptance source covers representative catalogue/schema behaviour, solution/project/document selectors, search, symbol resolution/info, stale context after reload and rename staging/commit/conflict paths. It was inspected but not run because repository policy does not authorize an automatic acceptance run when no acceptance artefact changed. It does not provide external-repository traces for most symbol-detail/hierarchy tools, cycle detection, flow analysis, disposables/nullability, API surface or test impact, and it asserts scenario completion rather than the four candidate semantics above.

## Earlier-unit revisit, conclusions and limitations

Bundled consumers were revisited against Units 1–3. Coordinate-bearing queries and both mutations use the intended Workspace snapshot validation; handler contexts remain immutable and transaction staging stays Host-owned. Workspace reference/hierarchy/target-framework caches remain snapshot-scoped, and no bundled handler introduces a cross-plugin cache key. Every bundled response is object-valued, so Unit 3 candidate `RWMCP2-006` does not make a bundled tool unusable. No correction to the architecture map or prior subsystem reports was required.

No additional substantiated defect was found in tool registration cardinality, destructive annotations, required mutation snapshots, project/document scope selection, deterministic top-level ordering, AsyncFixer package activation, successful/no-change mutation staging, transaction capacity enforcement, direct filesystem ownership, DI lifetimes or configured schema publication. Roslyn MCP navigation was unavailable in this environment, so current-source navigation used repository search and official Microsoft Learn API documentation; no symbol refactor or production edit was performed. External repository scenarios and acceptance tests were not executed, and stack exhaustion was established from the current recursive call path and plausible generated graph shape rather than deliberately crashing the review Host. Review stops here with unit 4 complete; units 5–8, repository-wide passes, independent final candidate validation and production remediation have not begun.
