## Test topology and enforced boundaries

The solution contains six ordinary unit/contract projects, four integration projects, one published-process acceptance project, one Code Action audit project and two shared support projects, plus the Workspace lock executable and seven plugin fixture libraries. `test/Directory.Build.targets` derives the required assembly category from project suffix, rejects category/suffix disagreement, and blocks ordinary unit projects and `TestSupport` from referencing `IntegrationTestSupport`. This keeps the intended boundary split mechanically visible: ordinary tests may use the smaller Moq/in-memory support graph, while integration and audit projects may consume production composition, MSBuild loading, materialised workspaces and built-in provider composition.

The unit projects reference their production assembly and `TestSupport`; their assertions generally terminate at one service/tool boundary and frequently substitute dependencies. The four integration projects reference real participating production projects through `IntegrationTestSupport`: Workspace exercises MSBuild-backed loading, transaction/recovery and the cross-process lock fixture; bundled Core exercises tools over a real component Workspace; Code Actions composes controlled and built-in providers; Host exercises DI, plugin loading, schemas, MCP adapters, Sentry projection and startup prerequisites. These tests cross more production boundaries than the unit graph, but they remain in-process and do not prove published distribution, stdio lifetime or filesystem/process isolation.

The acceptance project has no production compile reference. Its fixture project references are build-only (`ReferenceOutputAssembly=false`), and the assembly fixture publishes a Release Host into a unique temporary root. Individual tests copy readable Workspace templates and compiled external plugin packages, launch the published executable through the official MCP stdio transport, invoke public MCP operations, close stdin through client disposal and retain failed roots only when explicitly enabled. This genuinely exercises the distribution/protocol/process boundary it claims, including real plugin package discovery; it does not independently prove the packed plugin-authoring NuGet surface, which is instead covered by `PluginAnalyzerPackageIntegrationTests` building a clean consumer against a locally packed package.

The fixture assets are isolated by fresh materialisation. `WorkspaceAssetMaterializer` overlays explicit profiles, applies deletion manifests and excludes generated/state directories; acceptance copies assets beneath a per-scenario temporary root. The external plugin fixtures are production-shaped assemblies rather than linked test handlers. The Host integration package-consumer test packs `Roslyn.Workbench.Mcp.Plugins`, inspects its archive, restores a clean external consumer, proves analyser diagnostics on invalid source and then proves a valid source builds. These boundaries support the package and plugin conclusions from Unit 3.

## CI and suite enforcement

`.github/workflows/tests.yml` restores and builds the complete solution on Ubuntu, then runs category-filtered unit/contract tests, each of the four integration projects separately, and the published acceptance project on Ubuntu and Windows. Windows also repeats Workspace integration to cover platform-specific durable I/O and locking. Every lane writes TRX, uses a five-minute hang detector and enforces a fixed minimum count. Since the test runner's `total` counter includes non-executed tests, `Assert-TrxTestCount.ps1` proves that result files exist and enough cases were discovered, but by itself would not reject a future all-skipped or partially skipped suite; the current source declares no skipped/explicit tests, so this is a limitation of the guard rather than a current failing case.

The acceptance assembly itself republishes the Host even though the CI job already builds Release. This avoids silently testing a build output assembled through a test reference and gives every acceptance run a distribution-shaped Host. The fixture clears the build-time Sentry setting for the assembly lifetime, uses a non-inherited explicit environment for child Hosts, and uploads retained roots on CI failure. Process startup, invocation and shutdown have independent timeouts; the MCP SDK owns the child-process transport, while direct EOF lifetime coverage separately checks graceful shutdown.

The Code Action audit is isolated in `.github/workflows/code-action-audit.yml`, triggered for relevant pull-request paths, every main push, weekly schedule and manual dispatch. It fingerprints the complete built-in provider inventory and probes checked-in representative cases. A fresh execution in this unit produced 119 passes and one implement-interface failure out of 120, independently revalidating `RWMCP2-012`. Its source separately discovers a Roslyn action, calls the Workbench list operation only for visibility, and evaluates `GetOperationsAsync` on the original action object. It never takes the listed action ID through the reference store, resolver and stager, so the current audit still does not exercise the production replay boundary and independently revalidates `RWMCP2-013`.

The audit pull-request path filter is narrower than the complete production graph consumed transitively, but every main push and weekly run provide eventual enforcement. The more material weakness remains the harness boundary itself: even when green, it cannot detect a regression confined to stored-reference replay or mutation staging.

## Published Host and process trace

The representative published-process trace is: the assembly fixture resolves the repository root from assembly metadata, publishes the Release Host with the pinned SDK and WSL artefact routing where applicable, validates the executable, and exposes its absolute path through the acceptance environment. `AcceptanceProcessFixture` creates private per-test Workspace/state/plugin roots, copies checked-in inputs, starts `StdioClientTransport` without ambient environment inheritance, creates an MCP client under the initialisation timeout, invokes tools under per-call timeouts, and disposes the client to close stdin. Completion details and stderr are retained for diagnostics, while successful roots are deleted with bounded retries.

Failure containment is largely sound. Host initialisation failure records transport completion details when available, preserves a diagnostic exception, disposes the attempted client/transport and retains the root only under the explicit CI/local switch. Invocation failures mark the root for retention. Acceptance tests wrap assertion-bearing workflows and call `RetainRootOnFailure`; expected startup-failure cases are retained automatically by the published-host factory. The direct lifetime fixture owns its own process and termination fallback. No orphaned acceptance Host path was identified in the current ownership graph.

## External scenario runner topology

The scenario runner is a non-test console project included in the solution build but intentionally absent from ordinary CI execution. Platform wrappers restore pinned diagnostic tools, publish isolated Release Host/runner/cache-calibration plugin outputs, clear the build-time Sentry DSN for Host publication, pass absolute paths and remove only their unique publish root on exit. The runner loads the checked-in suite from its publish directory, takes an exclusive cache lock, prepares one pinned external repository, creates disposable execution/state roots, starts the published Host over raw stdio streams, drives the selected command, validates final state and writes retained JSON/Markdown/diagnostic evidence beneath the repository's ignored performance-results root.

The checked-in suite covers small, medium and large repositories and representative bundled query bounds, Code Action listing/Fix All/staging, plugin cache reuse/pressure/coalescing, durable create/replace/delete mutation, cancellation on both commit boundaries, controlled conflicts, forced crash recovery, external reload, live build, watcher stress, multi-revision history and multi-Workspace concurrency. It pins repository commit IDs and tool inputs. `ScenarioHost` owns its process, captures stderr, closes MCP/stdin normally, waits five seconds, then kills the complete process tree when required. External commands also kill their complete process tree on cancellation/failure. Counter collectors are killed in `finally`; direct EventPipe sessions request stop and await stream copying during asynchronous disposal; memory samplers cancel and join their sampling task.

Mutation-family iterations deliberately use a fresh Host. They capture failures, attempt rollback/Workspace close/Host disposal, inspect the repository after shutdown, restore changed tracked paths and newly created files with cancellation disabled, remove runner-owned Workspace state, and then validate commit identity, tracked cleanliness, recovery state, lock/state leakage and Host exit. Conflict and crash cases inspect recovery evidence before clearing it. The crash trace terminates the first Host only after an applied create/replace/delete is observable, starts a second Host against the same recovery directory, requires startup recovery to restore the pinned tree, reopens the Workspace and validates both shutdowns. This infrastructure reaches the filesystem/process boundaries claimed by Units 1–2 when it completes.

## Preparation, cache reuse and restoration

Normal first preparation clones with `--no-checkout`, checks out the pinned commit, runs repository-specific preparation with an isolated NuGet package root, then verifies HEAD and tracked cleanliness. Repeated runs reuse the commit-specific directory only after those same checks. A cache-wide exclusive file lock prevents concurrent runner processes from preparing or mutating any shared checkout. Repository restoration captures tracked paths relative to the pinned commit plus untracked files created after the iteration baseline, restores tracked paths in bounded Git batches, deletes newly created files and empty directories, and verifies both tracked and newly untracked sets.

The first-preparation failure path is not self-healing. The existence of `.git` is treated as proof that clone and checkout completed. If clone succeeds but checkout is cancelled or fails, the partial directory remains with `.git`; every later run skips checkout and fails pinned-HEAD validation. A preparation command that leaves tracked changes likewise makes the next run fail before preparation. Neither the manager nor wrapper quarantines/removes its runner-owned incomplete cache, so an ordinary transient/cancelled setup turns repeated preparation into a permanent manual-delete requirement. This is `RWMCP2-019`.

Restoration after a scenario iteration is materially stronger: all specialised mutation families perform it with `CancellationToken.None` after closing/terminating Hosts, even when execution failed. Cleanup failures are aggregated with the original failure. The validator intentionally checks tracked state, newly created Workspace coordination files and recovery state; ordinary read-only measurement/profile runs do not reject arbitrary untracked repository files, while mutation-family restoration separately accounts for new untracked files. No silent successful mutation-restoration path was identified.

## Failure, cancellation and evidence production

The runner keeps complete per-command evidence only in memory until every warm-up and measured iteration has finished. `measure` writes once after all selected scenarios; durable commit, commit cancellation, conflict, crash recovery and state sequence write once after all iterations; profile writes only after collection and workload completion. Each completed specialised iteration may already have performed Host shutdown, repository restoration and final validation, but those validation objects remain inside the in-memory measurement list.

Consequently, if a later scenario/iteration fails, a user cancels the run, result serialisation fails, or the process is interrupted, the command exits without writing earlier buffered measurements as a successful aggregate. Trace/counter files created directly may remain without a completion manifest, and cancellation during `File.Create` serialisation can leave a truncated file. Final disposition review established that this is consistent with the documented release contract: the whole command is one evidence unit, failure returns non-zero, and the operator reruns it from a clean state. The runner does not claim resumable or authoritative partial results, so `RWMCP2-020` is rejected rather than converted into journalling infrastructure.

Final state cleanup is not conditioned on successful evidence writing. The ordinary Host path closes the Workspace, optionally captures the post-close GC dump, disposes the Host, validates final state and writes `validation.json` before rethrowing an accumulated run failure. Specialised mutation paths restore and validate inside each iteration. The top-level execution directory is always deleted; deletion exceptions are intentionally swallowed for disposable state, while the retained output directory is separate. This avoids a misleading zero exit after a detected validation failure, but it does not preserve the completed evidence described above.

## Unit conclusion

The current test stack has meaningful layering and several genuine boundary tests: a clean packed plugin consumer, real MSBuild/component Workspaces, cross-process locking, published Release Host acceptance over stdio on Linux and Windows, and manual process/filesystem recovery scenarios. Its principal coverage weakness is the Code Action audit's replay label, already recorded in Unit 5. The proposed partial-evidence candidate was rejected because failed commands are intentionally rerun as complete evidence units. Review unit 8 and Stage 3 are complete.
