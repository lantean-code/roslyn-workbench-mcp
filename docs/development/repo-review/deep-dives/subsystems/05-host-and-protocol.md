# Deep dive 5 — Host and protocol

Date: 2026-07-31

Status: Complete

## Scope and composition map

The review covered the executable entry point, Generic Host composition, startup option parsing and projection, MSBuild registration, state-directory and recovery prerequisites, dependency-injection registrations and aliases, MCP server/stdio configuration, input binding, generated schemas, structured result envelopes, exception filtering, plugin and Code Action adapters, server-owned status/Workspace/transaction tools, shutdown behaviour and the focused unit, integration and retained acceptance evidence. Plugin package discovery, load-context isolation, collision policy and handler construction were revisited only where they enter Host startup; their implementation-depth conclusions remain in deep dive 3. Error capture, consent, report preparation and network dispatch remain owned by deep dive 6.

The composition root is short and ordered. `Program` creates the Generic Host builder, `HostStartupComposer` resolves configuration and builds the immutable Code Action/plugin catalogues, the builder extension maps immutable startup options into the subsystem option types, registers singleton Workspace/Plugins/CodeActions/Host services, materialises the complete static MCP tool catalogue, registers startup prerequisites and finally configures the SDK stdio server. The production dependency direction remains acyclic and only the Host references the MCP SDK. No temporary service provider, captive scoped service or incomplete alias registration survived current-source validation.

Startup execution has two phases. Configuration validation, Code Action catalogue creation, plugin discovery/composition and collision handling occur synchronously before `Build`. During Generic Host `StartingAsync`, MSBuild registration runs first, the configured state directory performs its security/writability initialisation, and unfinished commit recovery completes before the transport's ordinary `StartAsync`. Microsoft Learn's lifecycle ordering confirms that all `StartingAsync` callbacks precede hosted `StartAsync`, so the transport cannot admit requests before recovery. MSBuild discovery failure is deliberately converted into unavailable component status so `server-status` remains callable; Workspace loading then owns the later structured availability failure. State-directory operational failure remains fail-fast and is not silently redirected.

All Workspace state owners, catalogues, adapters and handlers use singleton lifetime by design. Per-call query or mutation leases, contexts and resolvers are created beneath those singletons and disposed by each adapter. Mutable singleton state is synchronised in its owning Workspace/cache/reference component. Current composition tests resolve the complete tool collection and verify the key alias identities. The review found no configuration option that was accepted but unused: each cache, concurrency, transaction, reference-lifetime, schema-mode, state-directory, plugin and error-reporting setting reaches its owning service, while full `server-status` intentionally omits sensitive or noisy paths and cache internals.

## Representative traces

### Clean startup, invalid configuration and prerequisites

Scalar command-line values override environment values, the final repeated scalar wins, plugin roots combine and deduplicate, and invalid individual settings fall back with durable `StartupConfigurationFallback` warnings. Error-reporting consent intentionally ignores the environment and fails closed when invalid. The resolved object is synchronously validated before plugin composition and also registered with `ValidateOnStart` as an invariant check. A real current executable run with a missing `--default-max-results` value confirmed that the surrounding Generic Host accepts the argument, the Workbench reports the fallback on stderr, state/recovery prerequisites complete, stdin EOF stops the transport and the process exits zero.

`StartupPrerequisiteLifecycleService` registers MSBuild, initialises the state directory and awaits recovery using the Host startup token. Focused physical integration coverage verifies MSBuild registration before Workspace creation and the state-directory/recovery ordering. The previous late state-directory writability defect is resolved as RWMCP-007; commit-time persistence validation remains necessary because availability can change after startup.

### Request binding and selector resolution

Every adapter inherits `McpServerToolBase`. It treats absent argument maps as empty, serialises the MCP dictionary under web naming, rejects missing required top-level members before deserialisation, enables nullable-annotation enforcement, rejects undefined top-level enum values and Flags bits, applies top-level DataAnnotations and maps JSON failures to a structured `InvalidRequest` without invoking the handler. Default-value publication is layered onto the SDK-generated schema from `[DefaultValue]`, and the same object is cached by request type.

RWMCP-027 is the retained boundary failure. Binding metadata is built for the top-level request only. The Workspace project contains exact semantic validation for every nested selector, but no production path calls it. Contradictory document, location and symbol selectors therefore reach precedence-based resolution, and inconsistent scopes can be silently broadened or emptied. A current-assembly probe also confirmed that the default `JsonStringEnumConverter` admits an undefined numeric nested `ScopeKind` and Host binding returns success. Unit tests prove the isolated validator and isolated binder, which masks rather than closes the missing connection.

### Schema publication and result envelopes

The Host asks the installed MCP SDK/System.Text.Json exporter for authoritative request and value schemas, normalises definitions and nullable annotations, publishes family-specific success/failure envelopes and caches composed schemas. Output schemas are omitted by default and generated only when `ToolOutputSchemaMode.Full` is selected. Query success returns `{ok:true,data:<response>}`, mutation success publishes the compact staged/summary/revision shape, and failure returns `{ok:false,error,next?,diagnostics?,warnings?}`. Server-owned tools map Workspace statuses into the same envelope. Unexpected failures add a correlation ID and local-detail/reporting availability without exposing the exception.

RWMCP-028 records a direct schema/runtime contradiction in Full mode. Value-schema normalisation collapses an object-or-null response to object, but both query adapter families intentionally serialise `NoChange` as successful null data. Current tests assert the null response but never validate it against the generated schema; a probe using the real current provider confirmed the non-null object schema. No other schema candidate survived: extra diagnostic/reporting properties remain allowed because the schema does not close object properties, the success/failure `oneOf` branches are distinguished by the `ok` constant, and current Host error/next schemas do not create a substantiated `$defs` collision.

### Plugin, Code Action and server-owned adapters

Plugin query adapters acquire a shared Workspace lease and cache scope, invoke the configured singleton handler and detect live Workspace mutation in `finally`; mutation adapters acquire the exclusive transaction lease, invoke a candidate-only handler and stage only through the Host-owned Workspace boundary. Code Action adapters use the equivalent internal contexts, replay stores and stager. All four pass the MCP request cancellation token into context acquisition, Roslyn/provider execution and staging, and dispose leases with `await using`. Cancellation remains cancellation through the top-level filter; unexpected non-cancellation exceptions are correlated once at the call-tool boundary.

RWMCP-029 records the one surviving metadata mismatch. The protocol factory mechanically marks every catalogue query idempotent. `list-code-actions` and `prepare-fix-all` are reference-producing queries: repeated identical calls create new GUID-backed replay recipes, change the returned IDs and consume bounded cache state. The repository already marks the analogous handle-producing `prepare-error-report` tool non-idempotent, so the current Code Action classification is inconsistent as well as operationally misleading.

The server-owned catalogue contains the unconditional local diagnostic/status, five Workspace and five transaction tools plus the two conditional external-report tools. Tool counts, reserved names and registration conditions agree. Workspace/transaction tools are thin cancellation-preserving projections into the lifecycle and transaction services reviewed in units 1 and 2. Their read-only, destructive, idempotent and open-world annotations are conservative and no tool was found to bypass the Workspace operation gate or transaction staging/commit boundary.

### Unexpected failures, stdout integrity and shutdown

The call-tool filter lets cancellation escape and catches every other tool exception. It logs the matching exception and random correlation ID, captures a bounded local record and returns a sanitised error envelope. Current tests prove cancellation propagation, message redaction, correlation matching, error storage and reporting-state projection. Capture/store/availability failures and external-report behaviour are deferred to the owning error-reporting deep dive.

The Host's own stream discipline is correct: it clears inherited logging providers and sends every configured log level to stderr. A real no-input run emitted zero bytes on stdout, placed framework/transport/lifetime logs on stderr and exited cleanly after EOF. Retained published-host acceptance covers the same process lifetime but was not rerun under the repository's explicit acceptance policy.

RWMCP-030 identifies the extension boundary that the clean-host evidence does not cover. Plugin exports are constructed and configured before transport startup and handlers run in-process during requests. Nothing reserves raw stdout against ordinary `Console.Out`, redirects extension console output, supplies an author-facing logging path or documents the restriction. One accidental `Console.WriteLine` can therefore precede or interleave JSON-RPC frames and make the entire server unusable. This is not a claim of sandboxing malicious trusted code; it is containment of the normal console logging API for cooperative plugins.

## Tests and evidence

Focused current-source evidence passed 245 Host unit/contract tests covering configuration, hosting, protocol, adapters, server-owned tools, registration and architecture, plus 34 Host composition/hosting/protocol integration tests. The SDK pinned by `global.json` is installed as .NET 10.0.102. A direct executable run validated fallback reporting, state-directory startup, zero Host log contamination, stdin EOF and graceful zero exit. Two read-only friend-assembly probes validated the exact disputed boundaries: undefined nested `ScopeKind` 999 binds successfully, and a class query response is published as non-null object data in the Full output schema.

The passing suites do not contradict the findings. Selector tests call `WorkspaceContractValidator` directly while binder tests use only top-level fields. Schema tests compare keywords and shape but never validate actual no-change payload instances. Protocol metadata tests derive idempotence mechanically from query kind and do not invoke reference-producing Code Action tools twice. Published and integration plugin fixtures emit no direct console output. Acceptance, Code Action audit and external-repository scenarios were not run because repository policy requires explicit authorisation or a later release gate.

## Findings and limitations

Independent current-source validation retained RWMCP-027, RWMCP-028 and RWMCP-030 as P2/high-confidence findings and RWMCP-029 as a P3/high-confidence finding. No P0 or P1 Host/protocol issue was substantiated. Configuration precedence, startup prerequisite ordering, Host DI aliases/lifetimes, ordinary adapter cancellation/disposal, sanitised unexpected-error mapping, server-owned lifecycle projection, Host logging separation and graceful EOF shutdown held up across their complete call paths.

Roslyn MCP tooling requested by repository guidance was unavailable, so local source and compiler/test navigation were used. Microsoft Learn was used for current Generic Host lifecycle and System.Text.Json enum behaviour, while the installed MCP SDK 1.4.1 XML contract was used for output-schema and annotation semantics. Direct console-output containment was established from source and clean-host negative evidence rather than a modified external fixture because production and test code were read-only for this review.
