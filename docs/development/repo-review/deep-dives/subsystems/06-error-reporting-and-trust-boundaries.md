# Deep dive 6 — Error reporting and trust boundaries

Date: 2026-07-31

Status: Complete

## Scope and composition map

The review covered top-level unexpected-exception capture, bounded local diagnostic models and correlation, local detail disclosure, provider-neutral external projection, prepared-report storage, consent and availability state, MCP preparation and submission tools, logging and Sentry dispatchers, Sentry client configuration and disposal, Workspace lifecycle invalidation, startup configuration and status projection, plus focused unit and integration evidence. Host binding, result envelopes and tool registration were revisited only where they carry error-reporting state; their implementation-depth conclusions remain in deep dive 5.

The subsystem is Host-owned and remains internal to `Roslyn.Workbench.Mcp`. `UnhandledToolExceptionFilter` is the sole automatic capture entry point. It logs the original exception locally, creates a random correlation ID, snapshots a bounded `CapturedErrorRecord`, stores it in a dedicated singleton and returns a generic error envelope. `get-error-details` exposes that record only to the connected local MCP client and labels it unsafe for external submission. `ExternalErrorReportProjector` is a separate allow-list transformation which discards exception messages, paths, Workspace identity and external-plugin names before either dispatcher sees the report.

Preparation and submission are deliberately separate. `prepare-error-report` projects one captured record, asks the selected dispatcher for a representative preview, checks the preview byte limit, computes a digest and stores an immutable `PreparedSubmission` under a random handle. `submit-error-report` accepts only that handle, evaluates process-local consent, optionally elicits a user choice, atomically moves one store entry from `Prepared` to `Sending`, dispatches the stored payload and records a receipt. The logging dispatcher writes one approved sanitised report to stderr. Sentry-enabled builds create one isolated DI-owned `SentryClient`; Microsoft Learn confirms that factory-created singleton disposables are disposed with the service provider, and Sentry 6.8.0 itself flushes its background worker for the configured ten-second shutdown bound during `Dispose`.

The principal architectural separation is sound, but the review found that the Sentry SDK boundary does not preserve the reviewed payload boundary as configured. The dispatcher mock tests inspect the deliberately minimal `SentryEvent` before the real client processes it. The real 6.8.0 client then runs its default `MainSentryEventProcessor`, whose defaults add a current submission stack trace, loaded assembly names and versions, culture/time-zone, memory/thread-pool and runtime/device contexts. Those fields are neither in the returned preview nor covered by its digest, and stack/module data can disclose paths and private assembly or plugin identifiers explicitly listed as excluded.

## Representative traces

### Unexpected failure and local diagnostic capture

A non-cancellation tool exception reaches `UnhandledToolExceptionFilter`, which creates a GUID, logs the exception to stderr, snapshots timing, tool classification, a maximum four-exception chain, up to eight frames per exception and the selected Workspace's coarse and local identity fields. Field lengths and the final serialised record are reduced against the configured byte ceiling before `CapturedErrorStore.Add`. Capacity eviction and lookup-time expiry are protected by one lock. The response contains only the generic failure, correlation ID, local detail-tool pointer and reporting availability; neither exception text nor type crosses that response.

Local inspection is intentionally a trusted-client boundary. `get-error-details` returns the stored immutable record with `sensitivity: LocalDiagnostic` and `safeForExternalSubmission: false`. Unknown and logically expired IDs are rejected. The store never retains a live `Exception`, Roslyn object graph, environment block or process command line. No automatic capture path invokes report preparation or either dispatcher.

RWMCP-032 records the retention defect beneath those otherwise effective bounds. Expiry is enforced only by `Add` and `TryGet`; neither store owns a timer or hosted cleanup operation. A lone captured record containing exception messages and source paths can therefore remain strongly referenced indefinitely after its advertised one-hour expiry while the server is idle. Prepared external payloads and receipts have the same lazy-only removal behaviour. Lookups correctly reject expired handles, so this is physical sensitive-memory retention rather than protocol reuse, but it contradicts the documented absolute-lifetime removal claim.

### Sanitised preparation and reviewed payload

Preparation reads the local record, rechecks reporting availability, creates a random report ID, invokes the provider-neutral projector and stores a dispatcher-owned preview and the same immutable `ExternalErrorReport`. External plugin tool names become `external-plugin-tool`; exception types become one of five coarse classifications; only Roslyn Workbench, Roslyn and .NET stack component categories survive; Workspace ID is removed; exact messages, frame names, source paths and external assembly names are absent. Focused projection tests seed sensitive paths, tokens, private type names and Workspace IDs and confirm their absence.

The logging dispatcher preserves this boundary: its preview is the exact JSON later serialised into the structured stderr log entry. The Sentry dispatcher also creates a deliberately minimal representative preview and a matching minimal `SentryEvent`, but RWMCP-031 occurs after that point. `ISentryClient.CaptureEvent` creates a scope and applies the option-owned processors. In Sentry 6.8.0, `AttachStacktrace` defaults to true, `ReportAssembliesMode` defaults to `Version`, and `MainSentryEventProcessor` adds current stack/thread data, every loaded non-dynamic assembly and several runtime contexts before the envelope is queued. Host composition disables global mode, sessions, logs, metrics, client reports, redirects and default PII, but does not disable these processors or enforce a final outbound allow-list. The approved digest therefore authenticates only the preview, not the actual diagnostic content sent over the network.

### Consent-required and consent-free submission

`never` prevents publication of preparation and submission tools while retaining local diagnostic inspection. Invalid command-line consent fails closed to `never`, and the similarly named environment variable is ignored. `always` bypasses only elicitation; an explicit prepare and explicit submit remain necessary. Prompt mode checks the prepared submission's Workspace ID and epoch, requires MCP form elicitation when no temporary grant exists, and maps submit-once, Workspace, session, decline, cancellation and session suppression into bounded process-local state. The elicitation identifies the stored destination and preview digest, and the submit request cannot replace either.

Ordinary sequential behaviour is fail-closed. Decline discards that handle, cancellation retains it only until logical expiry, suppression blocks preparation and submission, and Workspace grants are removed by the Workspace lifecycle observer on close or epoch change. One `PreparedSubmissionStore` lock prevents two callers from acquiring the same handle; an in-progress duplicate receives a stable rejection and a completed duplicate receives the original receipt.

RWMCP-033 records a cross-service time-of-check/time-of-use gap. Consent state is read before the submission-store acquisition and no consent generation or authorisation lease is carried into dispatch. A submit call can read `AllowedForWorkspace`, pause, then a concurrent `workspace-close` can synchronously invalidate that grant before the submit resumes, acquires the handle and dispatches. Two simultaneous prompt flows for different handles can similarly let one user choice suppress the session while another already-returned approval proceeds without observing suppression. Each individual service is locked, but their separate locks do not make authorisation and transition atomic.

### Repeated submission, network behaviour and shutdown

The prepared store serialises `Prepared`, `Sending` and `Sent` transitions. Accepted dispatch records the provider reference and preview digest; subsequent calls return that receipt without invoking the dispatcher. Explicit rejection and thrown/cancelled dispatch restore `Prepared` so the handle can be retried. The logging dispatcher is synchronous. The Sentry dispatcher treats successful SDK queue admission as acceptance and does not await remote ingestion; this is explicitly documented rather than reported as a defect. A later network failure is owned by the SDK background worker, and normal service-provider disposal asks it to drain for ten seconds. Abrupt process termination can still lose queued events, and no current test exercises a real failed transport or shutdown drain.

The current Sentry adapter creates a fresh SDK event ID each time it constructs a `SentryEvent`; the security re-audit's residual-risk statement that ambiguous retries reuse one Sentry event ID is inaccurate. The ordinary built-in call path nevertheless prevents a second dispatch after queue admission, because Sentry 6.8.0 catches capture failures and returns an empty ID when enqueueing fails, while a successful enqueue is immediately recorded as sent. The mismatch remains a documentation and future-dispatcher risk, but no second built-in provider call from one live handle was substantiated, so it was not retained as a separate finding.

### Availability, status and external destination controls

Unexpected error envelopes expose a coarse reporting state and preparation guidance. Full `server-status` exposes only provider name, configured consent mode and session-level consent state; `workspace-status` projects consent for the selected Workspace epoch. Neither reveals the embedded DSN. Reporting tool count and conditional publication agree with effective startup consent.

Sentry configuration accepts only an absolute HTTPS DSN with one project path, returns a non-sensitive destination label, disables automatic redirects and enables certificate revocation checking. The DSN is build input and is not accepted from runtime MCP input. The provider can still observe source IP metadata, as the public privacy documentation states. No mutable destination, redirect or credential-bearing result reaches the submission request or MCP response.

## Tests and evidence

Focused current-source evidence passed 52 Host unit/contract tests covering error capture and stores, external projection, availability, consent, preparation, submission, both dispatchers, Sentry policy and the top-level exception filter. Twenty-one Host composition, tool-composition and schema integration tests also passed. The .NET 10.0.102 SDK pinned by `global.json` is installed. Acceptance tests were not run under the repository's explicit execution policy.

The passing tests do not contradict the findings. Sentry dispatcher tests inject a mocked `ISentryClient`, capture the event at the call boundary and explicitly verify that no flush occurs; they never execute the real client's default processors or serialise the final SDK envelope. Store expiry tests advance `TimeProvider` and then call `TryGet`, which triggers lazy cleanup, but never assert removal without another store operation. Consent tests validate each state owner sequentially, and submission tests mock the consent service and prepared store independently; no test interleaves Workspace invalidation or session suppression between authorisation and acquisition.

The installed Sentry dependency is 6.8.0. Its tagged primary source confirms that `SentryClient.CaptureEvent` applies option-owned processors before queueing, `MainSentryEventProcessor` adds the unreviewed stack/module/runtime fields, `AttachStacktrace` and assembly reporting are enabled by default, and disposal performs a bounded flush. Microsoft Learn was used to confirm DI ownership and disposal of factory-created singleton services and `TimeProvider` timer cleanup expectations.

## Findings and limitations

Independent current-source validation retained RWMCP-031 as a P1/high-confidence finding and RWMCP-032 and RWMCP-033 as P2/high-confidence findings. No P0 issue was substantiated. The provider-neutral projection, local/external model separation, opaque handles, ordinary sequential consent paths, same-handle concurrency, HTTPS/redirect configuration, DI ownership and documented queue-admission semantics otherwise held up across their complete call paths.

The environment did not contact a real Sentry endpoint. Network failure, provider-side scrubbing/IP suppression and shutdown delivery were evaluated from current composition plus the pinned SDK's primary source, not live external traffic. Roslyn MCP tooling was unavailable and was not material to this Host-owned subsystem; local source navigation was used. The next programme unit owns test and operational infrastructure, after which the repository-wide passes must reconnect the new findings to release gates, cross-service concurrency and security claims.
