# 1.0.0 release readiness

## Status and purpose

This is the active preparation plan for the first stable Roslyn Workbench release. It is ordered by dependency: settle the supported product first, complete any missing distribution work, freeze the 1.x contracts, prepare release content, prove the exact candidate and then publish it through the established release process.

This document is a temporary worklist rather than lasting product guidance. When 1.0.0 is complete, move any durable decisions into the public or maintainer documentation and remove this file. Git history retains the completed checklist.

The release is not a reason to add speculative features. New implementation belongs in scope only when it closes an identified 1.0 contract, distribution, correctness, security, documentation or support gap.

## 1. Settle the 1.0 product boundary

- [x] Include and publish the separate `Roslyn.Workbench.Mcp.Plugins` authoring package as part of 1.0.0. Complete the independently reviewed work in [`../maintainers/plugin-distribution.md`](../maintainers/plugin-distribution.md) before the contract freeze.
- [x] Make an official MCP Registry listing a 1.0 launch requirement. Implement and validate the ownership, schema, icon and exact-version submission work described in [`../maintainers/roadmap.md`](../maintainers/roadmap.md); registry submission remains a separately authorised external action and must reuse the released NuGet package. Do not make client-specific or third-party catalogue publication a release requirement.
- [x] Keep plugin installation manual for 1.0.0 and do not launch a curated plugin repository. Accept external pull requests from 1.0.0 onward and require every contributed commit to carry a cryptographic signature that GitHub can verify; do not require a separate Developer Certificate of Origin sign-off or contributor licence agreement. Keep plugin discovery and trust decisions with users, and avoid any implication that third-party catalogue inclusion is a security endorsement.
- [x] Retain the current operating-system and architecture support matrix for 1.0.0: Windows x64, Linux x64 and WSL2 x64 are supported; macOS x64 and ARM64 remain best effort; Windows ARM64 and Linux ARM64 remain unsupported. Support the .NET 10 SDK line, with the minimum supported feature band determined from the release candidate. Support any local stdio client that implements the required MCP tool protocol; operations that require elicitation are supported only when the client advertises and permits elicitation.
- [x] Triage open defects, security reports, dependency alerts and known limitations. The 28 September 2026 triage found no open GitHub issues, Dependabot alerts, secret-scanning alerts or private security advisories. GitHub code scanning is deliberately outside the 1.0.0 scope, and a Snyk result is not a release gate. The accepted and documented residual limitations are the best-effort and unsupported platforms in the support matrix, trusted executable workspace and plugin inputs, support for SDK-style C# projects rather than every language and project system, client-dependent elicitation, and compiler-impact validation that does not replace third-party analyser validation or tests. No unclassified release blocker remains.

Exit condition: the exact products, registries, platforms, contribution model and known limitations included in 1.0.0 have explicit maintainer decisions.

## 2. Complete required distribution work

- [ ] Implement and review every distribution capability selected in section 1 without weakening the existing Host-only release path. Each independently published package needs deliberate identity, contents, dependency, provenance, trusted-publishing and documentation boundaries.
- [x] If the plugin-authoring package is selected, pack it with the calculated release identity; prove that it contains the Plugins and Abstractions contracts plus the authoring analyser without a Workspace implementation dependency; validate a clean external query and mutation plugin using only the package; and add exact package, symbol, checksum, SBOM, vulnerability, provenance and publication handling.
- [x] Confirm the Host `.nupkg` remains the sole Host runtime distribution and that both `dnx` and global-tool installation acquire the same exact package. MSI, MSIX, DEB and RPM artefacts must not reappear.
- [ ] Confirm NuGet.org trusted-publishing policies match every selected package ID exactly. Do not broaden the Host policy incidentally or fall back to a persistent API key.
- [ ] Confirm all credentials used during development and rehearsal are current, minimally scoped and absent from source, packages, logs and retained evidence; rotate any credential whose confidentiality is uncertain.

Exit condition: every product selected for 1.0.0 has a complete, independently gated release path and can be consumed without repository project references.

## 3. Freeze the 1.x compatibility surfaces

- [ ] Review the canonical built-in `tools/list` baselines for both output-schema modes as the intended 1.0 MCP contract. Resolve accidental descriptions, required properties, enum values, annotations, output fields and continuation guidance before declaring the baseline stable.
- [ ] Review the complete published stable error-code and `RequiredAction` catalogue. Confirm unknown-code behaviour and every continuation kind and target are suitable for the 1.x policy.
- [ ] Review recovery format V1, its explicit numeric enum values, current/supported format separation, immutable V1 fixtures and unsupported-version preservation. Exercise upgrade and downgrade guidance against the release candidate.
- [ ] Review `PluginApiVersions.V1`, the Plugins and Abstractions `PublicAPI.Shipped.txt` baselines and remaining unshipped entries. If the authoring package is published, preserve the exact 1.0.0 package as the future binary-compatibility baseline.
- [ ] Review every command-line switch, environment variable, operational mode, default and case-sensitivity rule. Remove pre-1.0 migration wording and make any final incompatible naming or default change before the contract freeze.
- [ ] Regenerate and review the security surface and invariant evidence from the exact compiled candidate. Every documented guarantee must map to current executable evidence, and unsupported scenarios must remain explicit.
- [ ] Approve [`../content/compatibility.md`](../content/compatibility.md) as the binding 1.x policy and ensure release notes separate changes to MCP tools, errors and continuations, recovery formats and plugin APIs.

Exit condition: the versioned surfaces are intentional, internally consistent, covered by immutable baselines and ready to receive the 1.x compatibility guarantee.

## 4. Prepare stable release content

- [ ] Replace the 0.1.0 beta template in [`../release/release-notes.md`](../release/release-notes.md) with 1.0.0 release notes covering the supported products, installation sources, platform matrix, operational defaults, compatibility guarantee, upgrade path, known limitations, security boundary and evidence.
- [ ] Remove beta, candidate-contract, pre-1.0 and “subject to change” wording from README and public documentation where the stable guarantee now applies. Preserve migration guidance only when a user can realistically upgrade from a published prerelease.
- [ ] Make installation, update, removal and client-configuration examples use the final package IDs, exact-version `dnx` form and supported operational modes. Verify all linked package, repository, support and security destinations.
- [ ] Review package metadata, embedded MCP metadata, icons, README, licence, third-party notices, repository identity, Source Link and deterministic portable PDB paths for every released package.
- [ ] Build the strict documentation site and inspect human pages, generated tool reference, agent guide and generated security reference. Confirm the first-production `/latest/` and site-root behaviour described in [`../maintainers/releasing.md`](../maintainers/releasing.md).
- [ ] Remove remaining temporary worklists, dated audits, obsolete dogfood material and superseded design documents. Run the tracked Markdown-link and external-reference checks after cleanup.

Exit condition: the repository, packages, release notes and documentation describe one consistent stable product with no obsolete prerelease promises.

## 5. Prove the release candidate

- [ ] Create the release branch through the documented GitFlow process and perform release-candidate work there. Keep version identity derived by GitVersion rather than manually editing package versions.
- [ ] From a clean checkout with the pinned .NET SDK, restore the Host graph in locked mode, build Release, run the complete unit/contract and component-integration suites, run latest-all analysis and run the full acceptance wrapper on Windows and Linux.
- [ ] Deliberately run the Code Action compatibility audit against the final Roslyn dependency set and review provider inventory, supported operations and failures. This establishes release evidence rather than adding the audit to every ordinary build.
- [ ] Reuse the extensive scenario-runner, memory and GC evidence already obtained when the candidate has not changed relevant runtime behaviour or dependencies. Rerun only the representative scenario families affected by later changes or any result whose identity cannot be related to the candidate; do not repeat expensive repository-size testing without a concrete question.
- [ ] Run the release workflow with publication disabled. Inspect the calculated version, exact `.nupkg` and `.snupkg`, release manifest, checksums, coverage evidence, SPDX SBOM, SBOM validation, dependency report and evidence index.
- [ ] Confirm the vulnerability gate covers every locked source project and every shipped private dependency, fails closed on incomplete scan data and has no unresolved high or critical finding. Review lower-severity findings explicitly.
- [ ] Validate exact-version `dnx`, clean global installation, `--version`, MCP startup, tool discovery, representative inspection and every mutation mode from the produced package on Windows and Linux. Validate plugin loading from a clean packaged consumer if the plugin package is in scope.
- [ ] Inspect packages and retained evidence for credentials, absolute source-machine paths, unintended files and non-deterministic identity. Verify GitHub attestations against an approved published release candidate when the live path is exercised.
- [ ] Record every validation command, candidate commit, result and any accepted limitation so the final release decision does not rely on an unidentified local run.

Exit condition: one exact release candidate commit has complete, reviewable evidence for contracts, correctness, recovery, packaging, security, documentation and supported platforms.

## 6. Rehearse the live publication path

- [ ] Publish an approved 1.0 release candidate through the same NuGet.org OIDC, GitHub attestation, GitHub Release draft and versioned-documentation path intended for stable publication. A local pack or publication-disabled run cannot prove external identity and permissions.
- [ ] Verify the release candidate anonymously from a clean environment: package visibility, exact-version `dnx`, global-tool installation, symbols, Source Link, documentation, checksums, SBOM, provenance and support/security links.
- [ ] Verify repository environments, Pages, NuGet trusted-publishing policies, GitHub token permissions, dependency/security features and branch protections described in [`../maintainers/releasing.md`](../maintainers/releasing.md). Treat unavailable external settings as outstanding rather than inferred success.
- [ ] Exercise the documented retry behaviour with evidence from the release-candidate path: matching drafts and documentation may be reused, while conflicting identities, published releases, duplicate packages and unreadable state fail visibly.
- [ ] Resolve every rehearsal finding in a new candidate and repeat only the affected evidence plus mandatory release gates. Do not promote an artefact that differs from the validated candidate.

Exit condition: the external publication, installation, documentation and verification path has succeeded with a release candidate using the intended production identities and permissions.

## 7. Publish 1.0.0

- [ ] Obtain the explicit maintainer go/no-go decision for the exact commit after reviewing all exit conditions, release notes, residual risks and external readiness.
- [ ] Merge the release branch into the production branch, create the exact stable `1.0.0` tag and merge that tag back into `develop` as described in the release guide. Dispatch the stable workflow against the exact production tag.
- [ ] Inspect the workflow's verified artefact and publication results before publishing the GitHub draft. Confirm package hashes, attestations, SBOM, vulnerability result, documentation identity, target commit and release notes all identify 1.0.0.
- [ ] Verify NuGet.org and any separately approved registry entry from a clean anonymous environment. Confirm `/1.0.0/`, `/latest/` and the documentation root resolve to the production documentation.
- [ ] Publish the GitHub draft as the latest production release only after package and documentation verification succeeds. Do not publish an incomplete draft left by a failed workflow.
- [ ] Perform a final installed-package smoke test and verify support, issue, discussion and private security-reporting routes from the public user perspective.

Exit condition: 1.0.0 is publicly installable, independently verifiable, documented and supported through the declared channels.

## 8. Close the preparation work

- [ ] Preserve the exact 1.0 contract and package baselines required for future 1.x comparison, including the first stable plugin package if one was published.
- [ ] Move any durable process correction discovered during preparation into the appropriate public or maintainer document.
- [ ] Remove this completed worklist and any release-only temporary files; retain release evidence in the GitHub Release and approved durable locations rather than the source branch.
- [ ] Triage early 1.0 feedback against the published compatibility and operating models. Do not reinterpret a stable contract from the former development plan.

The 1.0.0 preparation is complete only when every selected product boundary has either satisfied its exit conditions or been explicitly removed from the release with consistent public documentation.
