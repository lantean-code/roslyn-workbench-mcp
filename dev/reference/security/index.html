    Security guarantees and evidence

    Roslyn Workbench treats the connected local MCP client as authorised. These controls reduce mistakes, misfires, stale assumptions and unexpectedly broad operations; they are not an operating-system sandbox and do not defend against hostile code already running with the same authority.

    Enforced invariants

    Published operations expose bounded Host resource controls

    Actor: Roslyn Workbench Host

    Collection defaults, Code Action reference lifetime and concurrent query count are fixed by Host configuration and reported without exposing sensitive configuration.

    Boundary: These bounds apply to the corresponding Roslyn Workbench caches, references and query scheduling.

    Residual risk: Trusted Roslyn providers and build inputs can still consume substantial resources while an allowed operation executes.

    Covered surface:

    • status-field:codeActionReferenceLifetime
    • status-field:defaultMaxResults
    • status-field:maxConcurrentQueries

    Optional compiler-impact validation fails closed

    Actor: Roslyn Workbench transaction pipeline

    When configured, commit is blocked by new compiler errors or incomplete compiler evaluation relative to the transaction baseline.

    Boundary: The validation covers the projects and compilations affected by the staged transaction at commit time.

    Residual risk: It does not prove behavioural correctness, run all analysers or replace repository builds and tests.

    Delegated responsibilities

    The client and user remain responsible for intent and review

    Actor: Authorised MCP client and user

    The client should use inspection before mutation, convey elicitation failures accurately, review previews or receipts and keep each transaction to a coherent change.

    Boundary: Roslyn Workbench supplies bounded tools, structured continuations and exact review data; it cannot determine the user's true intent.

    Residual risk: A mistaken but authorised approval can persist an undesirable change that satisfies all mechanical safeguards.

    Workspace mutation requires coordinated local ownership

    Actor: Authorised MCP client, user and other local workspace editors

    Callers wait for recovery initialisation and avoid concurrent file edits or workspace-topology changes while non-cancellable commit application or recovery is in progress. A second Host instance sharing the same workspace remains advisory or query-only.

    Boundary: Roslyn Workbench detects many stale-input and external-change conditions, but it does not hold an operating-system lock over every workspace file or coordinate independent Host processes.

    Residual risk: Uncoordinated local writers can invalidate assumptions during the narrow persistence boundary and can require recovery or manual reconciliation.

    Limitations

    Roslyn Workbench is not a hostile-code sandbox

    Actor: Operating environment and repository owner

    Workspaces, builds, analysers, generators, Code Action providers and enabled plugins must be trusted for local execution.

    Boundary: The server is local and stdio-based, but trusted extensions and build inputs execute with the Host process authority.

    Residual risk: Hostile code with the same operating-system authority can bypass application-level controls and access local data directly.
