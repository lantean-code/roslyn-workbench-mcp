# Support and Feedback

Use the route that best matches what you want to achieve. Public reports and discussions are governed by the [Code of Conduct](CODE_OF_CONDUCT.md).

| You want to | Use | What to include |
| --- | --- | --- |
| Ask a setup, usage or troubleshooting question | [GitHub Discussions Q&A](https://github.com/lantean-code/roslyn-workbench-mcp/discussions/categories/q-a) | The Roslyn Workbench version, client, platform, goal and suitably redacted symptoms. |
| Explore an early idea | [GitHub Discussions Ideas](https://github.com/lantean-code/roslyn-workbench-mcp/discussions/categories/ideas) | The workflow or problem and who would benefit; a complete implementation proposal is not required. |
| Report a reproducible defect or performance regression | [Bug report form](https://github.com/lantean-code/roslyn-workbench-mcp/issues/new?template=bug.yml) | Release and environment identity, reproduction steps, expected and actual behaviour, and redacted evidence. |
| Report a documentation problem | [Documentation problem form](https://github.com/lantean-code/roslyn-workbench-mcp/issues/new?template=documentation.yml) | The page and documentation version, your goal, and what was missing or incorrect. |
| Propose an actionable feature | [Focused feature proposal form](https://github.com/lantean-code/roslyn-workbench-mcp/issues/new?template=feature.yml) | The problem, workflow, intended behaviour, impact, alternatives and compatibility implications. |
| Report a vulnerability | [Private vulnerability reporting](https://github.com/lantean-code/roslyn-workbench-mcp/security/advisories/new) | Follow [SECURITY.md](SECURITY.md); never use a public Issue or Discussion. |
| Report a Code of Conduct concern | Email `lanteancode@gmail.com` | Keep the report private and include only information needed to investigate it. |

## Diagnostic submissions

Roslyn Workbench can prepare a bounded error report for review and submit it only through its explicit, user-approved error-reporting workflow. Review the prepared fields before approving submission and use the option that removes the exception message when it may contain sensitive information. This mechanism is for consented diagnostic reports to the configured application provider; it does not create a GitHub Issue.

If the reporting tools are unavailable or submission is not approved, use the Bug report form only when the remaining evidence can be safely redacted. Do not post source code, credentials, personal data, private paths or secrets.

## Maintainer review

Issues and Discussions are reviewed at least weekly and before a release decision. This cadence is for triage and does not promise an individual response or resolution time.

Maintainers use the documented [Issue triage](.github/TRIAGE.md) and [Discussions](.github/DISCUSSIONS.md) processes.
