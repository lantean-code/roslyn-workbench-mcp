# Deep dive 4 — Code Actions

Date: 2026-07-31

Status: Complete

## Scope and dependency map

The review covered the complete current `Roslyn.Workbench.Mcp.CodeActions` implementation, its Host adapters and service registrations, Workspace execution and mutation boundaries, Abstractions selectors/results, Roslyn provider and operation contracts, active Code Action design and validation documents, all focused unit and component tests, and the claims made by the audit, acceptance and external-scenario evidence. Dependency direction remains acyclic: Host owns MCP publication and composition-root registration; CodeActions owns the internal three-tool catalogue, Roslyn MEF composition, discovery, replay and Fix All orchestration; Workspace owns immutable execution leases, candidate processing and transaction staging; Abstractions owns neutral selectors and result contracts. CodeActions does not depend on Plugins or the MCP SDK, and third-party plugins cannot acquire its internal services.

The executable surface is exactly `list-code-actions`, `prepare-fix-all` and `stage-code-action`. Host registers each typed handler and MCP adapter as a singleton. Invocation-specific Workspace leases, contexts, resolvers and effective Solutions are created per request; the composition, provider selection, analyser index, diagnostic service, replay-reference state, policy, resolvers, evaluator and stager are process singletons. The only mutable singleton owners are the synchronised reference cache and Roslyn's process-cached analyser index. No captive-lifetime, disposal or dependency-injection registration defect survived validation.

Configuration is declared and consumed coherently. Startup validates and projects the five-minute default reference lifetime and the 40,000–250,000 retained-recipe capacity range into CodeActions options. Composition is static and built-in by default; the exact 250-provider inventory and compatibility policy are pinned by the audit project. The Host uses the same composed `HostServices` to load the Workspace and activate providers, avoiding a MEF/Workspace service-identity split.

## Representative traces

### Listing and nested action identity

The Host query adapter acquires a shared Workspace lease and calls `ListCodeActionsTool`. Document and optional UTF-16 range resolution occur against the lease's immutable Solution. Refactorings invoke every eligible C# provider for the requested span. Code Fix discovery first intersects caller IDs with composed providers' fixable IDs, computes compiler, project-analyser and selected built-in-analyser diagnostics, groups diagnostics by exact source span, invokes each matching provider and flattens nested actions to leaves. Policy removes excluded providers and `CodeActionWithOptions` leaves before a reference is created.

Each returned leaf stores a process-local replay recipe containing the exact Workspace snapshot identity, project-aware document path, provider ID, action kind, nested path, title, equivalence key, diagnostic IDs and stable diagnostic identities. Projection sorts deterministically and bounds returned leaves and diagnostic contexts. RWMCP-025 identifies the one retained contract failure: reference-cache admission refusal is treated as if the leaf never existed, so saturation can turn an applicable result set into a successful empty or partial list with a false `totalCount`.

### Ordinary replay, stale references and unsupported operations

`stage-code-action` acquires the exclusive mutation lease before resolving its reference. Resolution validates the caller snapshot, reference expiry, Workspace ID and epoch, exact immutable snapshot identity, project-aware document and stored span. It re-invokes only the originating provider and requires exactly one leaf matching every stored identity component. Unknown or expired references become `ActionExpired`; a current-Workspace but different revision becomes `SnapshotMismatch`; unavailable, missing or duplicate matches become `ActionAmbiguous`. References for reachable undo/redo revisions remain stored but cannot execute while non-current; lifecycle observers actively remove unreachable branches, completed transactions and closed or superseded Workspaces.

The resolved Roslyn action is materialised with the current Solution and cancellation token. Evaluation accepts exactly one `ApplyChangesOperation`, ignores only the pinned wrapping bookkeeping operation and rejects every other operation shape. Microsoft Learn confirms that a Code Action may produce at most one `ApplyChangesOperation` and that other operations require host-specific behaviour. The candidate Solution is never applied directly: Workspace validates source-only project deltas, propagates supported added-document contexts, reconciles linked text, revalidates, checks the transaction baseline and stages a new revision. Multiple source documents therefore use the same transaction, preview, history, rollback and commit boundary as plugin mutations. Successful Workspace staging consumes the reference; rejected, conflicted and no-change results do not.

### Fix All preparation and staging

Preparation replays the originating ordinary Code Fix, verifies that the requested document, project or solution scope is still advertised, asks the provider for a new Fix All action, evaluates its operations and passes the candidate through the same Workspace candidate processor used by staging. It counts changed regular source documents only after propagation, linked reconciliation and post-merge validation, enforces the caller's maximum, publishes bounded project-aware affected-document identities and stores only a new replay recipe carrying the chosen scope. It does not alter transaction state or source files.

Staging a prepared reference first replays the exact originating leaf, recreates the scoped Fix All action on the same snapshot, evaluates it again and submits the resulting candidate through the ordinary Workspace mutation path. This avoids retaining Roslyn actions or Solutions in the cache and ensures source-only validation is repeated. RWMCP-026 identifies the retained project/solution-scale defect: `GetAllDiagnosticsAsync` implements a project-wide request by invoking a whole-compilation diagnostic and analyser pass once per source document plus once for project diagnostics. Preparation and staging both recreate the operation, so large Fix All workflows pay that work twice.

### Composition, policy and failure containment

MEF composition resolves the pinned Roslyn default and feature assemblies, creates one `MefHostServices`, activates C# exports through a narrow compatibility adapter and publishes unavailable component status rather than failing Host startup when assembly resolution, composition, export activation or metadata inspection fails. Provider selection filters excluded provider IDs and rejects duplicate eligible identities. Built-in analyser activation is lazy, process-cached, filtered by requested diagnostic IDs and isolates expected construction, metadata and execution failures into bounded warnings during list discovery.

Potential provider-exception, duplicate-provider and diagnostic-warning candidates were not retained. Provider invocation failures are unexpected trusted in-process Roslyn failures and are contained by the Host's correlated exception boundary; the current pinned provider inventory is unique and audit-gated; and no current source path substantiated a successful, materially incomplete Fix All caused by a discarded analyser warning. The output `CodeActionLocation` comment incorrectly says line and column are zero-based while the shared `ResolvedLocation` contract and implementation are one-based, but current public documentation does not state a conflicting basis and the wire values remain consistent with the shared contract, so this is documentation drift rather than a release finding. The unused symbol/location/scope request-resolution helpers left after removal of dedicated Code Action tools are cleanup debt without a current failure scenario.

## Tests and evidence

The focused current-source suites passed 262 CodeActions unit tests, 17 CodeActions integration tests, 29 Host Code Action adapter/composition unit tests and seven Host composition integration tests on the pinned .NET 10.0.102 SDK. Unit coverage exercises composition failure, provider identity, policy, analyser activation, compiler/project/built-in diagnostic collection, nested flattening, recipe construction, cache expiry/capacity/lifecycle concurrency, exact replay identity, prepared Fix All recreation, operation allow-listing, candidate impact measurement, request resolution, the three typed handlers and MCP adapter consumption/serialisation. Integration coverage exercises real built-in composition, compiler and IDE diagnostics, ordinary built-in staging, controlled option exclusion, multi-revision replay retention/eviction, two-document Fix All preparation/staging, Host service materialisation and the standard transaction path.

The passing suites do not disprove the findings. The list test explicitly expects a reference-creation failure to disappear from bounded metadata, and no Host response assertion requires a capacity warning or rejection. `WorkspaceFixAllDiagnosticProviderTests` mock the diagnostic service and assert one document-service call per project document, so they prove aggregation order while hiding that every real call performs project-wide compiler and analyser work. The controlled integration fixture has only two source documents. The retained scenario evidence measures document discovery on large repositories but Fix All preparation and staging only on the small GuardClauses repository.

The Code Action audit suite, published-host acceptance suite and external-repository scenarios were not rerun because repository policy requires explicit authorisation or release-stage execution. Their retained 2026-07-30 evidence was inspected for claim scope: provider inventory and representative compatibility are strong, but they contain neither reference-cache saturation response assertions nor realistic project/solution Fix All diagnostic-scaling evidence. Roslyn MCP tooling was unavailable, so local source navigation was used; current Microsoft Learn API documentation was used to validate MemoryCache admission, Fix All diagnostic-provider and Code Action operation semantics.

## Findings and limitations

Independent validation retained RWMCP-025 and RWMCP-026, both P2 with high confidence. No P0 or P1 Code Action defect was substantiated. Strict snapshot replay, lifecycle invalidation, one-apply-operation evaluation, source-only Workspace staging, reference consumption after successful staging, cancellation flow and static MEF ownership held up across their complete call paths. Review units 5 through 7 and the final repository-wide passes remain outstanding; Host exception/schema behaviour and operational scenario enforcement will be revisited in their owning units.
