### RWMCP2-001 — Code Action ranges are not snapshot-bound

- **Concrete failure scenario:** A client opens one or more Workspaces and then ends the stdio session without explicitly calling `workspace_close`. - **Affected projects/subsystems:** `Roslyn.Workbench.Mcp`, `Roslyn.Workbench.Mcp.Workspace`, MSBuild/Roslyn and filesystem-watcher external boundaries; to be revisited in review unit 6.
- **Remediation direction:** Give one Host-managed owner an idempotent shutdown path that atomically prevents new acquisitions, drains/removes every session, invalidates lifecycle observers, and disposes every manifest and loaded workspace while attempting all cleanup even if one disposal fails; add an in-process Host shutdown test with open sessions.

Shutdown attempts status closure, manifest disposal and loaded-Workspace disposal for every drained session, then logs rather than propagates terminal cleanup failure. Unit and in-process Host integration coverage proves repeated drains, every-session cleanup, lifecycle ordering, failure logging and disposal of a real stored session. The solution build, 1,000 Workspace unit tests, 94 Workspace integration tests, 484 Host unit tests and 71 Host integration tests passed; affected `latest-all` analyzer builds were clean. - **Confidence:** High

- **Concrete failure scenario:** A commit reaches `Applying` and replaces a source file, then the process stops. ### RWMCP2-019 — Failed initial preparation poisons the shared scenario cache

- **Status:** Validated — retained in final findings
- **Severity:** P2
- **Confidence:** High
- **Location:** `tools/Roslyn.Workbench.Mcp.ScenarioRunner/Repositories/RepositoryManager.cs:23-80`; `tools/Roslyn.Workbench.Mcp.ScenarioRunner/Repositories/ExternalCommand.cs:8-43`; `tools/Roslyn.Workbench.Mcp.ScenarioRunner/Application/ScenarioApplication.cs:50-64`

A repository preparation command which exits after leaving tracked changes similarly makes the next invocation fail before preparation can run again.
- **Supporting call path/evidence:** `RepositoryManager.PrepareAsync` uses only `Directory.Exists(repositoryRoot/.git)` as its completed-cache discriminator. The clone and checkout are two separate awaited child commands with no temporary/quarantine directory and no failure cleanup. `ExternalCommand.RunAsync` correctly kills and joins the child process tree when cancellation/failure escapes, but it intentionally does not remove partial command output. On the next call, the `.git` branch is false and `ValidatePinnedCheckoutAsync` rejects the wrong HEAD or dirty tracked state with instructions to remove the cache explicitly. `ScenarioApplication` holds the cache lock around preparation but performs no repair/quarantine, and both wrappers preserve the OS-local repository cache across invocations. There are no scenario-runner tests for interrupted clone/checkout or failed repeated preparation.
- **Affected projects/subsystems:** `Roslyn.Workbench.Mcp.ScenarioRunner` repository/cache/command management; Windows and Linux release-validation wrappers; pinned external-repository preparation and all later scenario families using the shared cache.

On entry, distinguish a validated cache from incomplete runner-owned state and quarantine/remove only the exact incomplete directory under the exclusive cache lock. After a preparation command fails, restore tracked state or mark the cache incomplete so a repeat can self-heal. Add deterministic tests with a fake child command/cancellable Git seam for failure after `.git` creation and tracked dirtying.
- **Validation history:** 2026-08-13 — review unit 8 independently traced first preparation, cancellation/failure, complete process-tree termination, cache reuse and pre-preparation validation through the current manager, wrappers and suite orchestration. The Scenario Runner project built successfully with zero warnings/errors; it has no executable tests for this state transition.
